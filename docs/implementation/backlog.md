## Remaining

| # | Title | Scope | Dependencies |
|---|-------|-------|--------------|
| 010a | Draft & Page Draft Updates + Collaborators | DraftResource update and PageDraftResource update (both with MPS/YJS "politely fail" for active editing sessions), card draft publishing context endpoints, card draft collaborator management, page draft update. Requires detecting draft editing state — applies to both card drafts and page drafts. Blocked on draft handling verdict. | 010, 011 |
| 024a | Draft collaborator eligibility ergonomics | `add_collaborators`/`add_group_collaborators` are all-or-nothing: guru-server throws a generic `400 "Invalid collaborator"` if *any* target is ineligible, without indicating which. A valid user collaborator must be an ACTIVE team member with author rights on a collection (standalone drafts) or write access to the card (edit drafts); groups need author/publish rights on a collection (`DraftOperationService.instantiateValidUserCollaborator` / `instantiateValidGroupCollaborator`). Consider (a) a `contrib` helper to pre-filter via the eligible-collaborators search endpoint, and/or (b) documenting the all-or-nothing behavior + eligibility rules on the resource methods. Verified against prod during sc-156806. | 024 |
| 027 | Source Records — object write surface + sync protocol | **Highest-value half of the Sources gap for SDK consumers.** Iteration 009 shipped read-only inspection (`list`, `get`, `object_types`, `connections`, `get_connection`); a customer building and maintaining a *custom source* needs the object write surface. Four endpoints are published in the vendored spec, all under `/sources/{sourceId}/objecttypes/{objectTypeId}/objects/{externalId}`: `PUT` (`touchObject` — marks an object as part of the current full sync; **not** a create/update, despite guru-cli's backlog labeling it "Create/update record"), `PUT .../content` (`createOrUpdateObjectContent`), `PUT .../file` (`createOrUpdateObjectFile`, multipart), `GET .../metadata` (`getObjectMetadata`). Note the shape is objecttype-scoped — there is no flat `/sources/{sourceId}/records/{externalId}` in the spec (see 028). **Models:** `ObjectMetadata` already exists in `_generated.py` (`version`, `external_checksum`, `sync_number`, `modified_by`) but is **not exported** — add to `models/__init__.py`. **Plumbing needed:** (1) `HttpClient.put_file()` — only `post_file()` exists, and the file endpoint is `PUT` multipart with `file` as the form field; (2) per-request header support for `If-Match` (external checksum) on `touchObject` — `HttpClient` currently sets headers only at client construction; (3) map `412` to a new `PreconditionFailedError` in `errors.py` + `_raise_for_status` (currently falls through to generic `GuruApiError`) — `touchObject` returns 412 on checksum mismatch, which is a normal control-flow signal in a sync loop, not an unexpected failure. **Design question:** `syncNumber`/`externalChecksum` are an incremental-vs-full-sync protocol (cf. `ObjectType.current_sync_number`); decide whether the resource exposes them as raw kwargs or a `contrib` sync-session helper that tracks the sync number across a batch. All four endpoints declare **no response schema** in the spec, so verify actual response bodies against prod before typing returns. | 009 |
| 028 | Source Lifecycle — create/delete/trigger sync/definitions | The remaining Sources endpoints from guru-cli's backlog: `POST /sources` (create), `DELETE /sources/{sourceId}`, `POST /sources/{sourceId}/sync` (trigger sync), `GET /sources/definitions` (list source types). **Blocked on spec verification:** none of these four paths exist in the vendored `swagger.json` — and neither do `GET /sources` or `GET /sources/{sourceId}`, which iteration 009 implemented from guru-cli parity rather than codegen. So the source-management surface is either absent from the public spec or lives on an internal API. Before implementing, confirm each path against guru-server and either (a) refresh the vendored spec if they are published (cf. ADR-008, where the live spec already had what we were about to hand-author), or (b) hand-author models in `_manual.py` and record an ADR, as iteration 011 did for internal page-draft types. Request/response models for create may be partly available already — `SourceDefinition` and `SourceConfig` both exist in `_generated.py` (referenced by `Source`). Sequence after 027: records are the recurring, high-volume operation customers automate, while source creation is typically a one-time setup step often done in the UI. | 027 |

## Notes

- Phase 2 is complete. Six core resources cover 50% of all legacy py-sdk functionality.
- Iteration 007 (god class audit) confirmed that board operations (11% of methods) should not be implemented.
- Contrib is now split into two iterations: workflows (multi-step API calls) and content utilities (pure functions on HTML).
- The migration matrix in `docs/implementation/007-legacy-audit.md` maps every py-sdk method to its new-SDK equivalent or category.
- **Sources rank higher here than in guru-cli.** guru-cli's backlog is ordered by *agent value*, where source management scores low — an agent reads knowledge, it doesn't provision pipelines. The SDK inverts this: building and maintaining a custom source is programmatic, repetitive, and CI-driven, which is exactly what a customer reaches for an SDK to do. Treat 027/028 as customer-facing priorities, not ports of low-priority CLI items.
- Iteration 009's `list`/`get` were built from guru-cli parity, not codegen — the vendored spec publishes no `GET /sources`. Assume the Sources surface in `swagger.json` is incomplete and verify against guru-server before trusting its absence as "endpoint doesn't exist."
- Each iteration follows the compound engineering loop: `start-iteration` → TDD → ADRs as needed → `complete-iteration` (implementation record + learnings + architecture update + CLAUDE.md patterns).
