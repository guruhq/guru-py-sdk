| 027 | Sources: API scoping (engineer-led) — **gates the undocumented surface only** | **Not an SDK task.** A sources engineer determines which APIs are required to stand up a source and ingest records; the SDK is only ever a wrapper around whatever that surface turns out to be. Deliverable: a confirmed list of path/verb/body/response per operation, enough to write resource methods against. **Why this blocks everything:** the documented Sources surface is 7 operations and covers only the middle of the pipeline. Records can be written (`PUT .../objects/{externalId}/content`, `.../file`, `GET .../metadata` — all returning `ObjectMetadata`) but a new source cannot be created, and **no write operation on `objecttypes` exists in either spec** — yet every record write needs an `objectTypeId` in its path, so the documented endpoints are unreachable for a fresh source. There is also **no sync lifecycle endpoint**: `touchObject` and the `syncNumber` query param both reference "the current full sync," but nothing documents how a sync is started, advanced, or completed, so even the documented record endpoints can't be driven correctly. Questions to resolve: (1) how a custom source is created via API — `SourceConfig`/`SourceDefinition` are published schemas that no path consumes, so the shapes may already be correct; (2) how object types and their fields get defined — `Source.source_object_types` is a `list[ObjectType]`, hinting they're declared inline at creation rather than via a separate endpoint; (3) where `syncNumber` originates and who advances it (cf. `ObjectType.current_sync_number`), and what marks a full sync complete; (4) whether record deletion is implicit — `touchObject`'s existence suggests untouched objects are swept at the end of a full sync, which would mean no delete endpoint exists *by design*; (5) whether `GET /sources` and `GET /sources/{sourceId}` are supported-but-unpublished or internal, since iteration 009 already ships both. Likely owner: the sources team (James Ahlborn). | 009 |

## Notes

- Phase 2 is complete. Six core resources cover 50% of all legacy py-sdk functionality.
- Iteration 007 (god class audit) confirmed that board operations (11% of methods) should not be implemented.
- Contrib is now split into two iterations: workflows (multi-step API calls) and content utilities (pure functions on HTML).
- The migration matrix in `docs/implementation/007-legacy-audit.md` maps every py-sdk method to its new-SDK equivalent or category.
- **Sources rank higher here than in guru-cli.** guru-cli's backlog is ordered by *agent value*, where source management scores low — an agent reads knowledge, it doesn't provision pipelines. The SDK inverts this: building and maintaining a custom source is programmatic, repetitive, and CI-driven, which is exactly what a customer reaches for an SDK to do. Treat 027–029 as customer-facing priorities, not ports of low-priority CLI items.
- **The Sources work is shaped scope → wrap → demonstrate, and the SDK layer stays shallow.** 027 is engineer-led API scoping (not an SDK task); 028 wraps whatever surface that confirms with thin typed methods and no orchestration; 029 shows it working via two `contrib` examples (file-based and record-based ingestion). Any sync bookkeeping loop belongs in `contrib`, not in `SourceResource`. **027 and 028 are not strictly sequential** — the documented record endpoints and the `HttpClient` plumbing can be wrapped before 027 lands, so the implementer picks the order. Only the undocumented surface genuinely waits on 027.
- **guru-cli's backlog mislabels the record surface** — it lists a flat `POST/GET/PUT/DELETE /sources/{sourceId}/records/{externalId}` and calls the bare `PUT` "create/update record." Neither is right: the real paths are objecttype-scoped (`/sources/{sourceId}/objecttypes/{objectTypeId}/objects/{externalId}`), and that `PUT` is `touchObject`, which only marks sync membership. Don't port those rows verbatim.
- Iteration 009's `list`/`get` were built from guru-cli parity, not codegen — the vendored spec publishes no `GET /sources`. Assume the Sources surface in `swagger.json` is incomplete and verify against guru-server before trusting its absence as "endpoint doesn't exist."
- Each iteration follows the compound engineering loop: `start-iteration` → TDD → ADRs as needed → `complete-iteration` (implementation record + learnings + architecture update + CLAUDE.md patterns).
